# Owner access

One creator claims Siluet from the local server terminal, sets a password and enters the studio without a media key. The first PR replaces the status page with Svelte setup, sign-in and a protected home. Use the [approved studio layout](../design/workspace/index.html) for the sidebar, mobile drawer and light/dark appearance. Show only working destinations.

## First PR

**Startup.** Put the embedded Turso database in a per-user data directory (absolute `SILUET_DATA_DIR` override, owner-only access). Only an absent or empty directory may be initialized. On first initialization, persist an installation ID both in a private marker file and in the database. On subsequent starts, check for both files before opening the database in existing-file mode. Missing files, mismatched IDs, unrecognized migrations or a failed migration stop startup with a redacted error. Before issuing a token, verify the database’s claimed state agrees with the singleton owner row. Interrupted initialization must recover consistently or stop without offering setup.

**Origin.** The launcher sets the Bun adapter’s `SILUET_SERVER_ORIGIN` from the selected numeric loopback host, HTTP scheme and concrete port before starting each built server process. The built entry rejects an absent or non-concrete origin. Default to `http://127.0.0.1:3000`. For port zero, select a free loopback port, start a child with that port and matching origin. If the bind collides, select another port and launch a fresh child with its own origin. Announce setup and the token only after a successful bind. An explicit origin must match the listener. Reject forwarded-header overrides. Check the original Host on application requests and require the canonical Origin on mutations. Keep SvelteKit’s form-origin check enabled.

**Claim.** After successful startup, print the working setup URL and a separate random token (at least 128 bits) to the operator terminal. Keep the token in memory, replace it every 15 minutes while unclaimed and on restart, and print its replacement. Check it before expensive password work and again at commit. Validation errors and transaction rollback leave a still-current token usable. One transaction inserts the database-enforced singleton owner, marks the installation claimed and creates a session. Only the winner receives a cookie. The token is unusable after commit.

**Credentials.** Trim the username, normalize it to NFC and match it case-sensitively (1–64 Unicode code points, no control characters). Accept passphrases of at least 15 code points and at most 1024 UTF-8 bytes, allow paste and password managers, and hash with Bun’s asynchronous Argon2id. Retain the normalized username, hash and creation time. Sign-in gives the same failure response and verification work for an unknown username and an incorrect password. Limit claim to five failed token checks and sign-in to ten per five minutes across the installation, including concurrent attempts. Throttling expires automatically.

**Sessions and routes.** Store a digest of each random session token, its owner, creation time and last activity. Expire sessions after seven idle days or 30 days total and purge expired records. Valid sessions survive a restart. Set a host-only HttpOnly cookie with `Path=/`, `SameSite=Lax` and an explicit Secure flag derived from the trusted scheme. Same-origin POST sign-out revokes the record and clears the cookie. It also writes a fresh random UUID to a separate, port-named cookie. Open tabs read this public value to discard private drafts, even if the owner signs back in before a tab resumes.

The server hook protects application routes and actions by default. Health and public UI assets stay available. Before claim, private page requests lead to setup. After claim, setup closes and signed-out page requests lead to sign-in. Unauthorized private actions fail before doing work. Authenticated users land on the studio home. Auth and private responses use `no-store`. Exclude tokens, passwords, hashes, session cookies and query parameter values from diagnostics, error pages and form responses.

## Acceptance

- Start the built server with a temporary data directory and port zero. Force the first candidate port to be occupied. Verify that only the successful process announces setup and that Chromium can claim at its printed URL. Use the keyboard to reach the desktop sidebar. Retain that browser session and restart with the same data and origin. Verify that it still opens the studio, then sign out and verify access is revoked. From a fresh browser context, verify the old token cannot claim again, a private page requires sign-in, and the original credentials open the studio. Check the mobile drawer, light and dark appearances and public health response.
- Exercise token rotation and expiry, concurrent claims on independent connections, rollback, wrong credentials, throttling, session expiry/revocation, cookie flags, Host/Origin validation and redaction. After a successful claim and shutdown, remove only the database and leave the marker intact. Test that case, damaged storage and a failed migration and verify setup stays closed and no token is emitted.
- Keep the storage transaction behind focused database functions, the flow in a server service, and SvelteKit actions thin. Update the existing README’s start instructions and run the [development checks](../README.md#development).

## Follow-up PRs

Offer optional authenticator enrollment after claim and in Security settings. Activate TOTP after a verified code. Keep its seed encrypted under an owner-readable key separate from the database, show recovery codes once, store their hashes and consume codes and accepted time steps atomically. A recovery code substitutes for the second factor after successful primary sign-in. Apply enabled MFA across all sign-in methods.

Offline recovery is an explicit host command for the existing owner. With the service stopped, prompt privately for a new password, revoke sessions and pending proofs, clear old factors and suspend external bindings until reverified. Preserve studio data. A missing factor key requires host recovery, even if the database remains readable. External sign-in setup follows the [owner sign-in decision](decisions.md#owner-sign-in).
