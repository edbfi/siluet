# PoYo.ai image and video API

Public documentation reviewed on 2026-11-21, starting with PoYo’s Kling Image 4.0 guide. The [model inventory](catalog.md) records exact submission IDs, operation coverage, model-specific inputs, and differences between the manuals and the published catalog snapshot. The [synthetic scenarios](scenarios.json) cover submission, polling and download recovery. Live availability, billing and output behavior remain unverified. [Starting guide](https://poyo.ai/hub/kling-4-0-image-api-guide)

## Submission and task identity

| Step | Documented contract | Evidence |
| --- | --- | --- |
| Submit | Server-side bearer key and JSON to `POST /api/generate/submit` with the exact `model` ID, model-specific `input`, and optional top-level `callback_url` where supported. A user-configured key can require a stable `X-End-User-ID` header. This header identifies a caller for provider access controls. | [API overview](https://docs.poyo.ai/api-manual/overview), [end-user identification](https://docs.poyo.ai/platform-security/end-user-identification) |
| Acknowledge | Check HTTP status and JSON business `code`. On acceptance, the documented response has `code: 200`, `data.task_id`, `status: "not_started"` and `created_time`. Save the opaque task ID for later recovery. A validation response can use HTTP 200 with business `code: 400` and `error.message` and `error.type`. | [Unified OpenAPI](https://docs.poyo.ai/openapi.json), [errors](https://docs.poyo.ai/api-manual/error-codes) |
| Poll | Bearer-authenticated `GET /api/generate/status/{task_id}` returns `data.status`: `not_started`, `running`, `finished` or `failed`. A terminal failure can arrive in a successful status response with `data.error_message` and empty `files`. A status lookup can itself fail. The polling guide shows a 404 with a top-level `detail` string. | [Task status](https://docs.poyo.ai/api-manual/task-management/status), [image status](https://docs.poyo.ai/api-manual/task-management/image-status), [video status](https://docs.poyo.ai/api-manual/task-management/video-status) |
| Receive callback | PoYo POSTs the terminal task object without the polling envelope. The `X-Webhook-Signature` is Base64-encoded HMAC-SHA256 over `task_id + "." + timestamp` using the webhook HMAC key. The timestamp is in `X-Webhook-Timestamp`. PoYo requires a publicly reachable HTTPS receiver that responds within 30 seconds. Verify the signature and handle duplicates. PoYo documents up to five delivery retries, starting around 60 seconds and capped at 10 minutes between attempts. A loopback-only deployment can recover the same terminal result by polling. | [Webhook contract](https://docs.poyo.ai/api-manual/task-management/webhooks) |
| Retrieve results | On `finished`, fetch the direct URLs in `data.files[]`. The common fields are `file_url` and `file_type`, with optional format, MIME type, name, size and label in the unified reference. Model-specific metadata can matter. Generated image and video files are documented as available for three days after creation. Billing details and task history have a three-month retention period. Per-file expiry timestamps and result URL renewal are unverified. | [Task status](https://docs.poyo.ai/api-manual/task-management/status), [retention](https://docs.poyo.ai/#8-data-retention-policy), [layer decomposition](https://docs.poyo.ai/api-manual/image-series/seedream-5-5-layerize) |

## Input media and uploads

Model fields normally take provider-fetchable URLs. Check the selected operation’s formats, byte and duration limits, cardinality, and ordering. The Kling references and Seedance 2.5 Flash require directly downloadable HTTP(S) URLs. Sora 2 Beta’s documented `image_urls` also accepts a Base64 image. An upload response’s `file_id` identifies the uploaded object. The cited model operations consume the returned URL. [Kling Image 4.0](https://docs.poyo.ai/api-manual/image-series/kling-4-0-image), [Seedance 2.5 Flash](https://docs.poyo.ai/api-manual/video-series/seedance-2-5-flash), [Sora 2 Beta](https://docs.poyo.ai/api-manual/video-series/sora-2-beta)

| Upload endpoint | Required input | Documented limits and lifetime | Evidence |
| --- | --- | --- | --- |
| `POST /api/common/upload/url` | JSON `file_url`, a publicly downloadable HTTP(S) URL | One JPEG, PNG, GIF or WebP. 72 hours. | [URL upload](https://docs.poyo.ai/api-manual/file-series/upload-url) |
| `POST /api/common/upload/base64` | JSON `base64_data`, raw Base64 or data URL | Same image formats, one per request. 72 hours. | [Base64 upload](https://docs.poyo.ai/api-manual/file-series/upload-base64) |
| `POST /api/common/upload/stream` | Multipart binary `file` | One image in the formats above or one MP4, WebM, MOV, AVI or MKV up to 100 MB. Images last 72 hours. The reference specifies 24 hours for video under the default `temp/videos` lifecycle prefix. Custom video-path lifetime is unverified. | [Stream upload](https://docs.poyo.ai/api-manual/file-series/upload-stream) |

The upload methods accept a bearer key and optional `file_name` and `upload_path`. They return `success` and business `code`, plus `data.file_url`, `download_url`, `file_id` and `expires_at` on success. The methods document a 10-request fixed minute window per authenticated user per endpoint. A model may accept assets the upload API cannot host. For example, Seedance 2.5 Flash documents direct video references up to 200 MB each and MP3 or WAV reference audio. The upload endpoints above document image and video support. [Upload schemas](https://docs.poyo.ai/api-manual/file-series/upload-stream.json), [Seedance 2.5 Flash](https://docs.poyo.ai/api-manual/video-series/seedance-2-5-flash)

## Retries, cost and progress

- PoYo explicitly says submission retries are not deduplicated. A missing acknowledgement, transport timeout or ambiguous server error leaves acceptance uncertain. The public references provide no client-generated reconciliation key or lookup by the original request. The dashboard history can assist manual investigation. Siluet decision D1 reserves any potentially duplicate submission for the creator. Once a task ID is known, recover by polling the same ID. PoYo recommends polling every 2–5 seconds, backing off on 429 and transient 5xx, and honoring `Retry-After` where present. The quickstart documents a default account limit of 20 generation submissions per 10 seconds and says requests rejected by that limit do not enter the queue. [Retry guidance](https://docs.poyo.ai/integrations/troubleshooting#retry-decisions), [quickstart](https://docs.poyo.ai/), [polling guidance](https://docs.poyo.ai/api-manual/task-management/status#polling-best-practices), [decision D1](../../decisions.md#d1--one-creator-on-one-machine)
- PoYo publishes prices by model and bills successful generation. The status response can supply `credits_amount`, including in running task examples. Use the terminal amount for recorded charges, with absent amounts treated as unknown. Pricing varies by output count, resolution, reference inputs, output or billed seconds, or tokens. Kling Image 4.0 lists 13/19/32 credits per 2K/4K/8K image plus reference fees. Seedance 2.5 Flash applies a different per-second rate when video references are used and includes their rounded-down durations in billed seconds. The long-image model uses skill, length and resolution tiers. `GET /api/user/balance` returns account credits. An exact per-request preflight quote or a charge lookup after lost acknowledgement is unverified. [Pricing](https://poyo.ai/pricing), [launch prices](https://poyo.ai/changelog), [Kling guide](https://poyo.ai/hub/kling-4-0-image-api-guide), [CLI billing FAQ](https://poyo.ai/cli), [balance reference](https://docs.poyo.ai/api-manual/account-management/user-balance)
- The reference defines `progress` as an integer from 0 to 100. Its update frequency, monotonicity, availability by model, queue position, and relation to remaining time are unverified. Use the task status to recognize terminal states. Kling’s published timings range from roughly 45 seconds for one 2K image to about 30 minutes for a 10-image 8K series. These are examples of elapsed time. [Task status](https://docs.poyo.ai/api-manual/task-management/status), [Kling Image 4.0](https://docs.poyo.ai/api-manual/image-series/kling-4-0-image)
- A provider task can finish while its download or local write fails. Keep the task ID and the provider’s terminal result. Retry the affected file when possible within its lifetime. The public status contract provides direct files and has no documented mechanism to regenerate an expired URL or deduplicate a new paid submit. [Task status](https://docs.poyo.ai/api-manual/task-management/status), [retry guidance](https://docs.poyo.ai/integrations/troubleshooting#retry-decisions)

## Synthetic contract scenarios

The JSON document uses `request` and `response` for mock HTTP exchanges. A `fault` describes injected transport or download behavior outside the provider body. `expect` states the intended observation in a future test. Task IDs, prompts, messages, timestamps and download URLs are illustrative. Match requests at the mock boundary and intercept every `example.invalid` download. The fixture contains no credential placeholder for test code to send.
