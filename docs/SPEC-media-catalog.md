# Media catalog

**V1 · Approved by council under the owner’s delegation on 2026-11-22.** Defines the coverage ledger for [D2](decisions.md#d2--full-image-and-video-model-coverage). The creator can find the image and video operations Siluet supports, see which connected route can run a request, and understand why another route is unavailable. Contributors can reconcile Siluet support against a finite, dated set of public provider evidence.

## Inventory and identity

Use the [dated evidence ledger](media-catalog.v1.json) for public model IDs, routes and operations. Include documented operations whose primary result is an image or a video, including translation, layer decomposition and media transformations. Track media operations that depend on a prior non-media task with that prerequisite. Standalone text, audio, moderation and 3D remain outside D2. Classify by the documented result, since provider categories and endpoint names can differ from it.

Use `(provider, model ID, route, operation)` as the registry key. Preserve model ID spelling and case, including suffixes and slashes. Represent first-frame animation, first-and-last-frame interpolation, mixed-reference generation, source-video editing and task-based extension independently when they have different request or result contracts. Use the operation name and, where needed, a variant note to distinguish input roles. The adapter owns the exact wire mapping. Keep resolution, duration, count and other choices within the relevant operation unless the provider gives them a separate ID, route or operation contract. Expand groups in the ledger into distinct keys before computing coverage. A listed ID with an unknown operation or route remains a discovery gap and adds no verified operation to the denominator.

The JSON ledger defines `providers`, `families` and `supportProfiles`. Provider `sources` map short keys to official links. `discovery` records the source dates and snapshot scope. ToAPIs `listings` distinguishes snapshot entries, regional listings and IDs found only in model documentation. A `rows` entry applies its `media`, `route`, `operations`, `contract` and `sources` to every exact identifier in `ids`. `documented` rows have an exact submit route and operation evidence. `advertised` and `unresolved` rows use a null route and an empty operation array, with `advertisedOperations` for claims that need an exact contract. `gaps` carry specific unresolved details. The top-level defaults leave key access and D4 unknown, require review of the option contract, and mark each row as inventory coverage until an operation names a support profile. A `catalogD4` value preserves a discrepancy with the direct REST evidence. A conflict in either record blocks Queue until the competing evidence is reconciled. A per-operation `requires` entry records the prerequisite kind and whether creating it is within D2. Report prerequisite-bound operations separately. Only shipped support profiles describe what a creator can Queue at the recorded application baseline.

Family and model labels group choices for browsing. Preserve the provider, route, exact ID and operation when a creator selects a choice. For example, Seedream 5.5 groups Poyo.ai `seedream-5.5` and ToAPIs `doubao-seedream-5-5` for ordinary generation and reference editing. Poyo’s `seedream-5.5-layerize` and ToAPIs’ `layer_decomposition: true` remain distinct operation keys. Apply an explicit alias only to the documented members. A provider switch reruns validation, clears staged references as today and requires a fresh Review.

## Evidence, coverage and availability

- **Evidence** records a pinned revision or observation date, official contract links and unresolved discrepancies. A catalog listing can establish the advertised ID or endpoint family. A model-specific contract establishes an operation, payload and media result. Carry missing and conflicting information forward, including optional fields, types, defaults, combinations, uploads, results and expiry. Keep app-ready request and result rules with the provider adapter and its focused tests. The ledger indexes the rules and gaps without copying upstream schemas or pricing. The [catalog engine](SPEC-catalog-engine.md#deriving-and-validating-rows) is the one exception, recorded on 2026-11-26: it derives rows from a committed projection of the pinned Poyo.ai catalog, kept with its MIT notice and digests under `scripts/media-catalog/sources/`, because mechanical validation needs the exact schema offline. The ledger itself still copies none of it.
- **Siluet support** is tracked per key, from inventory to Review to Queue and saved output. For Queue and save, give the supported input and output envelope. A covered operation with partial options remains partial for D2. Pricing can be unknown under [D1](decisions.md#d1--one-creator-on-one-machine). Count discovered IDs, verified operations, unresolved discovery, and Review and Queue coverage independently. Reconcile additions, changes and removals in reviewed updates. Retain historical identifiers for existing jobs and Gallery items.
- **Key access** is a server-side observation tied to a credential revision. A successful ToAPIs model list can establish whether the exact ID was returned in the requested scope. A failed or stale check, or an endpoint family whose access is unclear, leaves that access unknown. Poyo’s balance check establishes credential acceptance. Its public catalog supplies no key-specific entitlement evidence. Keep provider access, operation support and model pricing independently observable. [ToAPIs model discovery](https://docs.toapis.com/docs/en/api-reference/chat/list-models) · [Poyo.ai public capability discovery](https://docs.poyo.ai/integrations/catalog)
- **D4** uses the exact fixed flag defined in [the decision](decisions.md#d4--optional-filtering-on-media-requests). Record an explicit conflict when the applicable closed request schema excludes it or the contract forbids it. Record unknown when the contract is silent or acceptance or effect is unspecified. Surface the evidence in Review. Keep the shipped Seedream access gates on their existing API origins. Disconnected or unreadable credentials and an authoritative list that omits the model disable Queue. Unknown access permits Queue only under a released route’s explicit credential rule. A new live path requires an explicit credential-revision and API-origin access rule, a reviewed adapter and compatible supported input. ToAPIs uses the global toapis.com origin for this release. Under the 2026-11-26 [D4 revision](decisions.md#d4--optional-filtering-on-media-requests), a route with unknown D4 field acceptance queues with a Review disclosure, and a reconciled exclusion (closed schema or contract) queues after the Review acknowledgement with the field omitted. Disagreeing sources stay blocked until reconciled. Either clears only the D4 gate. Disclose field acceptance separately from eligibility for a provider's conditional fallback. Preserve a rejection and the original request semantics. Any change to the fixed flag or routing policy requires owner approval.

For a released operation, the composer and server share the same operation key and validated values. The server resolves the key through the registry and revalidates the accepted Review before any upload or provider call. The existing Review, disclosure, retry, credential, job and Gallery guarantees apply. Treat public source content as evidence for a reviewed adapter change. The composer, Review and Queue consume the repository’s reviewed registry locally. Preserve request and result contract versions where a changed adapter would otherwise alter an existing job or an accepted Review.

## Production baseline

At the ordered-reference release `3a2432b`, [Image Studio](SPEC-image-studio.md) supports one ordinary Seedream 5.5 output per request on both providers. The [ordered edit](SPEC-seedream-multi-reference-edit.md) accepts 1–10 ordered public HTTP(S) image URLs under one reference-edit operation key per provider. Local-file edits, retries and layer decomposition have separate release prerequisites. Poyo’s production connection currently sets the Seedream flag after a successful balance read. ToAPIs sets it only when the scoped model list includes `doubao-seedream-5-5`. The [workspace design model list](../design/workspace/models.js) demonstrates family grouping and a small set of image and video choices. Its fixture connections, inferred inputs and price estimates do not count as production support.

## Release and acceptance

1. Reconcile and approve the evidence ledger. Every ID in the frozen source scope has a documented operation, an unresolved discovery row or an explicit out-of-scope reason. Validate evidence references, exact-case model IDs, unique expanded operation keys, aliases, and explicit unknowns. Catalog refreshes show the evidence diff before they affect coverage or app behavior.
2. Introduce the offline registry through the four existing Seedream generation/edit paths. Test both providers independently, key replacement and unknown access, partial options, and unchanged reviewed request and saved results. Map `text-to-image` to the existing `generate` estimator and `reference-image-edit` to `edit`. Preserve decryption of existing credentials with their original authenticated data, and replay already claimed Reviews by their original job IDs. Test both with pre-upgrade records.
3. Expand Image Studio with a reviewed adapter slice such as Poyo’s Z-Image generation, which already has a local rate. Check ToAPIs video availability using its video-scoped model list. Qualify Poyo `h3-max` and ToAPIs `seedance-2-5` text-to-video independently for Video Studio. Each publishes the required field and a prompt-only request. Extend video in slices for keyframes, mixed references, edit and extension. Approve upload, disclosure, billing, polling, download and retention contracts before enabling each applicable path. Include documented acknowledgement, confirmed failure, uncertain submission and failed download in fixtures. Use the same coverage criteria for both providers.
4. Reconcile remaining media operations and option gaps against the approved baseline, including disagreements between sources and D4 blockers. D2 is complete for a dated baseline only when every in-scope operation and its option envelope are supported on its own provider, and every unresolved in-scope discovery and option gap is closed, or the owner approves an explicit scope change. Publish separate progress for discovery, documented operations, implemented operations and option gaps.

Keep browser-safe registry values under `src/lib/shared/` and provider-specific request, result and access rules under `src/lib/server/providers/`. Keep tests beside those rules, use fresh provider fixtures only where a new contract needs them, and run the [development checks](../README.md#development). Live billable verification requires express owner approval.

## Scope

Include prerequisite-bound cover art and music-video operations because their primary output is in scope. Qualify references to existing owner-accessible music tasks separately from any standalone music-generation workflow.
