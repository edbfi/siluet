# Live image batches · V1

**Milestone 3, approved.** The owner can send one reviewed Seedream 5.5 draft several times, track each request in Jobs and save any successful image to Gallery. This extends [offline Review](SPEC-image-studio.md) and depends on the existing [single-image flow](SPEC-first-saved-image.md) and [ordered URL edit](SPEC-seedream-multi-reference-edit.md). The ordered-edit baseline is tree `f907bce1934f9c0db24e47583b8ab1f8e43044b8`. [D1](decisions.md#d1--one-creator-on-one-machine) governs access and spending.

## Scope and Review

- Use one connected provider and one validated draft for **1–5 requests**, with **0–3 extra attempts per request**, defaulting to zero. Each request uses the same prompt, model, options and ordered references, and asks for one ordinary image. Send a separate POST for each attempt. A request stops after its first success. One request with zero retries uses the existing single-job path, including its quote, consent, replay, tracking and Gallery rules.
- Scope live batches to text-to-image and edits with 1–10 distinct ordered public HTTP(S) URLs. Preserve the existing model validation, exact trimmed URL strings and array order. Show the ordered hostnames and disclose that each attempt sends the full signed URLs, prompt and options to the selected provider and its applicable upstream services. Apply the existing retention and fallback disclosures and show the redacted outgoing payload. Siluet performs zero reference lookups, fetches or uploads. Files and mixed references remain available in offline Review. Layer decomposition, per-request drafts and local-file hosting are deferred. Both providers document uploads. Poyo.ai returns an accessible URL and documents 72-hour image retention, and ToAPIs returns a public URL. The upload contracts leave charges unspecified, so this slice authorizes no uploads or hosting spend. [Poyo.ai Seedream](https://docs.poyo.ai/api-manual/image-series/seedream-5-5) · [ToAPIs Seedream](https://docs.toapis.com/docs/en/api-reference/images/seedream-5.5/generation) · [Poyo.ai uploads](https://docs.poyo.ai/api-manual/file-series/upload-stream) · [ToAPIs uploads](https://docs.toapis.com/docs/en/api-reference/uploads/images)
- Compose and Review with zero external calls. Use the shared local calculator for dated per-request and initial-batch estimates in provider credits. The initial estimate is the per-request price multiplied by the request count. Always show the maximum number of potentially billable POSTs, `count × (1 + retryLimit)`, up to 20. When a rate covers the draft, also show the estimated spend if every allowed POST were charged at that rate. For example, two requests with one extra attempt apiece at 5.6 credits show an initial estimate of 11.2 and a maximum-attempt estimate of 22.4 credits. Include reference charges through the existing calculator. The number of POSTs is the enforced limit. Actual spend has no verified provider-side cap at the quoted rates.
- Missing rates, uncovered inputs or evidence at least 30 days old produce an unknown total with the reason. Update an open Review at expiry. Keep a verified unit rate when usage determines the total. Show a known ToAPIs standard-route estimate even when fallback is possible, with the overall maximum spend marked unknown in that case. Require explicit unknown-cost acceptance for unknown totals and for possible unpriced fallback, including when eligibility is unknown. Review explains that each retry is a new submission that may charge credits. Selecting a positive retry limit and clicking **Queue** with that limit visible authorizes those extra attempts. Clear acceptance when any reviewed term changes. ## Authorization and dispatch

Apply signed-in owner and same-origin checks on Review and Queue. Enforce integer bounds and the full draft contract on both POST endpoints. Bind the opaque Review to the owner, exact canonical provider payload and ordered URLs, operation, credential revision, counts, retry policy, quote and version of the disclosures shown. Use the installation-keyed binding for durable replay and include the exact acceptance in the claim. On first Queue, recheck the terms from local state and atomically claim the Review, record the batch and reserve its request slots. Changed terms require an updated Review and a fresh click before provider traffic. Concurrent and later identical replays return the original batch across restarts, expiry and key changes. Mismatched replays fail. Replay issues zero provider calls and starts no work.

The first claim starts a server-run dispatch window of two minutes from acceptance. On the Review tab, before enabling Queue, show the count, retry limit, potentially charged attempts, per-request, initial and maximum-attempt estimates, background dispatch and the applicable batch cost consent. Explain that dispatch can continue if the owner leaves the page. Warn in Settings before changing a credential with an open dispatch window, including backoff and settlement waits. Freeze the payload, reference order and retry choice at claim. Later composer edits affect only a new draft. Send first attempts in request order before any retries. Then send due retries in request order, one POST at a time, and track acknowledged tasks independently. Before each attempt, recheck the credential revision, price evidence and disclosure version and atomically reserve the next attempt against the original limit and current credential revision. A changed term or elapsed window stops further sends, leaves those requests visible with the reason and requires a fresh Review and Queue for new work. Credential replacement or removal that wins this reservation race prevents the send. A reservation that wins can use that reviewed key for its one send. Immediately before starting the POST, recheck the dispatch deadline after any balance read or pacing wait. If expired, durably close the reservation as skipped before send and close any zero-send wallet interval without a comparison. Disable automatic transport resends. Persist the send reservation before the POST and record a valid acknowledgement or definitive rejection durably. A failure after acknowledgement leaves siblings eligible within the accepted window. A definitive submit-time validation, filtering, credential or quota rejection stops further sends of the identical payload.

Keep the prompt and full ordered reference payload only in transient memory during the dispatch window. Retain the accepted terms and minimal request/attempt ledger in Turso, including status, task IDs, timestamps, revision, mapped reasons, charge evidence and output links to local Gallery records. Keep prompts, reference hosts and URLs, signed result URLs, keys, filenames from the request and raw responses out of history, logs and persistent browser storage. On restart, recover acknowledged tasks by their original IDs, retain recorded outcomes, and mark requests known never to have been sent as **Not submitted**. If an attempt ended definitively and the next one was never reserved, show the recorded outcome and that the remaining attempts were skipped. A reserved send with no durable acknowledgement or definitive rejection becomes **May have been submitted**, even if it might have stopped before the POST. Never resume a paid send from a recovered batch. A new send after interruption needs a fresh Review and Queue.

## When an extra POST is allowed

A retry uses the exact same reviewed payload and consumes one of that request's extra attempts. It requires positive retry consent in the accepted Review, a durably recorded qualifying outcome, and time remaining in the dispatch window. Use exponential backoff with jitter and honor any longer `Retry-After`. Use one provider-wide submit gate for batch and single requests, across credential revisions. On a confirmed throttle, pause every submit through the shared gate until its local backoff expires, extended by any longer Retry-After. Persist that deadline across restart even when the header was absent. The existing one-request, zero-retry path keeps its documented uncertain outcome after a sent 429. An exact limiter signature still closes the shared submit gate for every path. If that gate is already closed at first use of a single-job Review, return the next permissible send time before claiming or sending and require a fresh owner click. Recheck the gate immediately before the single POST in the same send-start serialization used by batch sends. If a throttle arrives after first claim while the single job is reading its starting balance, persist the known unsent outcome and next allowed time, close its wallet interval without a comparison and require a fresh Review and click. Replaying the old claim returns that same unsent job. Never wait through a cooldown on behalf of a claimed single job. Apply the documented submit limits even without a throttle response. A cooldown longer than the dispatch window leaves remaining requests unsent. Keep status reads within the existing per-task window and cooldowns, including after restart. Share a local ceiling of two status reads per second per provider across single and batch jobs. Honor any stricter advertised query limit or cooldown.

| Provider | Qualifying outcome and billing evidence |
| --- | --- |
| Poyo.ai | A submit response with HTTP 429, body `code: 429`, `error.type: rate_limit_error` and no task ID or acceptance indication qualifies. Poyo.ai documents that requests rejected by this submit limiter never enter the queue. It says failed generation tasks are uncharged, but its Seedream status contract gives free-text failure details and no settlement indicator. A terminal `failed` or reported zero credits alone cannot establish a retryable cause. Never retry from that observation. [Submit limits and retry guidance](https://docs.poyo.ai/#10-rate-limits-concurrency) · [Error codes](https://docs.poyo.ai/api-manual/error-codes#429-too-many-requests) · [Task status](https://docs.poyo.ai/api-manual/task-management/status) · [Billing policy](https://poyo.ai/) |
| ToAPIs | A submit response with HTTP 429, `X-RateLimit-Category: async_submit`, documented `error.code: rate_limit_exceeded` and no task ID or acceptance indication qualifies as a rejected submit. An acknowledged task also qualifies if a successful query for the same ID reports `failed`, `error.reason` is `service_busy` or `request_rate_limited`, and `billing.status: refunded` confirms zero net charge with both amounts present and zero. Generic failure, pending or missing billing, and contradictory billing do not authorize a retry. Retain the failed task ID and keep settlement visible. Continue bounded automatic reads of a failed task only with a qualifying reason, pending or missing settlement, unused retry budget and an open dispatch window. Stop on refund, settlement, contradictory data, paused tracking or dispatch expiry. One successful automatic response must contain the same task ID, failed status, allowed reason, refunded state and explicit decimal zero for both credits and cost_usd. Never assemble this proof from different reads. Manual Refresh cannot arm a retry. Keep manual display evidence separate from automatic retry evidence. A manual read winning the race can update the display, but an eligible automatic read still needs its own reserved observation before the deadline. If they coalesce, count the response only for the origin that reserved the read. Respect the shared cooldown. Manual Refresh updates status and billing only. [Submit limits](https://docs.toapis.com/docs/en/api-reference/rate-limits/async-tasks) · [Failure reasons](https://docs.toapis.com/docs/en/api-reference/errors#task-failure-reason-lookup) · [Task billing](https://docs.toapis.com/docs/en/api-reference/tasks/image-status#billing-status-and-spend-tracking) |

These are the V1 allowlist. Poyo.ai explicitly documents no queue admission for its submit limiter. For ToAPIs, infer rejection before admission only from the exact async submit limiter signature. The limiter documentation gives no separate billing guarantee. Count every retry as potentially paid. Treat timeouts, transport errors, 5xx, other uncertain 429s, malformed or contradictory acknowledgements and missing durable outcomes as uncertain where submission cannot be established. An uncertain submission stops further attempts for its request. Jobs explains that it may still cost credits and points to provider history before the owner decides whether to create a separately reviewed request. Validation, filtering, unreadable reference, authorization and quota failures are never retried. A status-read error, missing task, unknown status or unavailable result only affects tracking or retrieval. Never switch provider, rewrite the payload, refresh a reference URL or drop a reference to recover.

## Jobs, billing and Gallery

Jobs shows the batch and each numbered request, its attempts used and available, last known progress, task IDs, and the outcome or reason it stopped. Show confirmed failure, uncertainty and requests known never submitted distinctly. Acknowledged tasks keep the existing **Refresh status** and credential-revision rules. Show admitted, rejected, uncertain and never-sent requests with their outcomes. A request with zero admitted tasks exhausted on the documented limiter reads **Not admitted · throttled** with its POST count and counts under rejected. If a prior task was admitted and failed, retain that task and count the request under failed, showing each later throttled attempt separately. Show counts of successful, failed, rejected, uncertain and unsent requests when dispatch ends, with pending or paused tracking visible. Successful rows save automatically ([D9](decisions.md#d9--save-automatically)). Save verifies and publishes at most one image per result. Failed or expired downloads leave generation history intact. Retry download uses the same task and never issues a generation POST. Saved images remain available locally after restart and provider disconnection.

Keep the accepted estimate, task amounts and wallet observations separate. Show Poyo.ai credits as reported by task with settlement finality unverified. Show ToAPIs settled charges or confirmed refunds by task. Show a confirmed ToAPIs total only when all attempts are accounted for and every potentially billable attempt has complete settlement evidence. An ambiguous send or an attempt with unverified billing leaves the total unknown. Label any sum of confirmed amounts as a known subtotal. Deduplicate by task ID and use decimal arithmetic when totaling. A slot with no send reservation has no charge. Any attempted submit lacking a task and a documented billing guarantee, including a definite rejection, leaves the total unknown. Require both decimal amounts in one coherent settled observation, or both zero in a refunded observation. Contradictory settlement evidence stays unverified. Missing amounts never become zero. The connected ToAPIs model key authorizes no wallet read. [Poyo.ai task amounts](https://docs.poyo.ai/api-manual/task-management/status) · [ToAPIs actual charges](https://docs.toapis.com/docs/en/api-reference/account/pricing/actual-cost) · [ToAPIs account balance access](https://docs.toapis.com/docs/en/api-reference/account/get-balance)

For Poyo.ai, open the wallet interval and mark overlap in the same transaction as the first attempt reservation, then take at most one before-balance before the first POST and one after-balance after all sent attempts have confirmed terminal outcomes or definitive rejections and the batch can no longer send. Use the same credential revision and the existing bounded wallet-read rules. Check that revision in the transaction storing the after-sample for both single jobs and batches. Discard the sample on mismatch. A batch with no reservation opens no wallet interval and reads no balance. A failed before-read permits authorized work. Display the dated difference as **account balance movement** because reservations, top-ups and other clients affect it. Withhold it for missing readings, key changes, any uncertain outcome or overlap with another Poyo.ai batch or single job. Mark both intervals on overlap, including work with no usable snapshot, and treat a batch's own attempts as one interval. An unresolved potentially debiting Poyo.ai submission suppresses later comparisons across key revisions. Media expiry and a stopped polling window leave that uncertainty open. ## Acceptance

Use fresh recording provider fixtures with Bun and Chromium against the built app. Confine fixture traffic to loopback, keep evidence beside the adapter tests and run the [development checks](../README.md#development). Billable verification requires separate express owner approval.

- On both providers, exercise generation and ordered signed URLs, counts 1 and 5, and retry limits 0 and 3. Verify one output per request, exact URL order on every POST, zero Siluet reference transfers, offline Review and no calls for direct bypass, tampered counts, invalid URLs or files. Verify dated prices, maximum-attempt arithmetic, stale and unavailable rates, and known ToAPIs standard pricing with unpriced fallback. Exercise keyboard Review at a narrow viewport.
- Race Queue, repeated tabs and Settings. Change the retry choice, a signed query or order before claim. After claim, edit the browser draft and verify subsequent sends keep the accepted values. Between sends change price evidence, disclosure or credential and verify dispatch stops. Replays of old single-job and new batch claims preserve their original IDs and issue zero calls. Inject interruption before the send reservation, after it, and after provider acceptance with no durable ID. Restart and verify unsent, uncertain and acknowledged requests, preserved attempt budgets, resumed status reads and zero resumed generation POSTs.
- Simulate each qualifying throttle, misleading 429 bodies, matching ToAPIs transient failure with refund, pending refund, contradictory billing, missing causes, non-retryable failure and lost acknowledgements on both providers. Test a before-balance read crossing the deadline, a headerless throttle with a competing single job, a competing batch throttle arriving during the single job’s starting balance read (zero single POSTs, durable unsent outcome and stable replay), both manual and automatic refund-read orderings, initial request order before retries, single and batch cooldown after restart, pending-to-refunded automatic reads, incomplete complementary observations, manual Refresh, confirmation of a submit-time rejection, retry exhaustion, dispatch expiry and mixed results, including an admitted failed task followed by a throttled final attempt. Count all outbound generation POSTs, including rejected sends. Refresh and Save must issue zero generation POSTs.
- Verify Poyo.ai balance movement for an isolated batch, then suppression on partial readings, overlap with a batch or single job, key replacement during an after-read, and unknown submission followed by key replacement. Check ToAPIs performs no wallet calls and deduplicates charges, including incomplete settlement. Save one success beside a failed request, simulate a failed download and reopen the saved bytes offline after restart. Check persisted records, URLs exposed to the browser, diagnostics and logs for planted secrets, prompt markers and reference components.
