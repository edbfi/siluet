# Seedream 5.5 edit with a local file

**Approved 2026-11-22 · Uploads 1.** Queue a Seedream 5.5 edit with one verified SDR JPEG or PNG, cleaned unless the owner turned cleaning off ([cleanup](SPEC-provider-media-cleanup.md#sending-originals)), one ordinary output and zero automatic upload or edit retries. Qualify both formats through [media cleanup](SPEC-provider-media-cleanup.md) before enabling them on each connected provider. Keep offline Review available for disconnected drafts and for multiple files, mixed URL/file references, other formats, batches, layers or retries where already supported. Explain why Queue is unavailable. Preserve text-to-image and the [public URL edit](SPEC-seedream-reference-edit.md), including ordered URL-only edits as they land. URL-only edits pass the input URLs directly to the provider.

## Provider contracts

Use the saved model key as the Bearer credential. Send one binary multipart `file` part with an application-generated filename and the verified `image/jpeg` or `image/png` MIME type. Use the default upload purpose or storage path. An acknowledged upload creates a hosted copy separately from the edit.

## Review and dispatch

1. Stage on the local server through the signed-in owner's same-origin POST. Preparation and Review make zero provider calls. Stream at most 32,000,000 original bytes per file. Qualify the built Bun listener with a supported image above its current 512 KiB default request limit. Use a raw file body up to 32,000,000 bytes for this local staging route and set the listener ceiling to that value. For other routes, retain the 512 KiB ceiling in the server hook, enforcing both declared and streamed length. Test an oversized chunked POST to an ordinary route. Allow up to 16,000,000 pixels, 16,384 pixels per edge, 8 MiB of decompressed descriptive metadata and profiles in total, one preparation at a time per installation and 30 seconds per preparation. Reserve each copy in the shared 128 MiB scratch pool ([cleanup](SPEC-provider-media-cleanup.md)) and reserve capacity before writing. If reservation fails, show **Local scratch full**. Refuse before writing any part of the new copy, preserve existing drafts and tell the owner to remove a staged file or wait for idle expiry. Test a full pool, zero partial files or provider calls, and successful staging after a release. Apply any lower qualified per-format limits during preparation. Enforce the provider's byte limit on the cleaned output. Neither model documents its reference pixel bounds. Release source bytes after verification. Bind the stage to its owner, session and opaque draft identifier. Verify that identifier on preview, Review and first Queue claim. Release idle copies on replacement, removal, cancellation and sign-out, and reclaim orphaned scratch after restart without touching another process's active transfer.
2. The creator previews the verified staged bytes in Review. Use an authenticated, session- and draft-scoped local response with verified MIME, `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff` and `Cross-Origin-Resource-Policy: same-origin`. Refuse any present foreign Origin (including null) or Sec-Fetch-Site outside same-origin and none. Describe the cleanup, surviving ICC fields and watermarks. Show the upload and edit separately in the outgoing preview, with fixed methods and endpoints, masked Bearer headers, multipart field and default path/purpose, neutral filename, verified MIME, size and a placeholder for the hosted URL. The stage expires after 15 minutes of inactivity. Staging or an explicit successful Review starts the idle interval. Passive previews, Queue attempts (including stale responses) and background activity do not extend it. After a stale file Queue, request an explicit Review for the current terms and deadline. At Review issue an immutable deadline 15 minutes from that Review. A later Review may extend the stage's lifetime, but an earlier token keeps its own deadline.

A different Review of the same stage cannot allocate or consume it concurrently. Keep the 128 MiB on-disk scratch quota independent of a 32,000,000-byte aggregate quota for in-memory dispatch buffers per installation. Atomically reserve the verified byte length against the buffer quota before reading. Keep the charge through multipart completion, and release every reservation on failure or completion. Compute the reviewed digest on that buffer and send the same bytes from it. Keep every writable alias and on-disk change out of the multipart body. ## Outcomes and acceptance

Classify upload responses independently of edit submissions. A ToAPIs HTTP 400 with `success: false` and no upload data, or a documented unambiguous validation, authorization or quota rejection without upload data, maps to a fixed rejection. Poyo.ai’s HTTP 400/413/422 validation detail, HTTP 401/403 authorization detail, and explicit failed business codes 400/401/402/403 without upload data map to fixed reasons. Discard detail strings and localized messages. Transport/body-read failure (including ToAPIs `read_request_body_failed`), HTTP or business 408/429/5xx, an unknown 404, and conflicting success/error or upload-ID/URL signals take precedence as uncertain. A consistent success acknowledgement establishing a stored object with an unusable URL, mismatched MIME or different byte count is **File uploaded · edit not sent**. An HTTP 402 with only undocumented detail and no matching documented Poyo.ai business code stays uncertain. [Poyo.ai upload response schemas](https://docs.poyo.ai/api-manual/file-series/upload-stream) · [ToAPIs upload errors](https://docs.toapis.com/docs/en/api-reference/uploads/images) An upload timeout, throttled or 5xx response, lost or contradictory acknowledgement, or interruption after the upload boundary without a durable outcome means **Upload outcome unknown · edit not sent**. A successful upload with an unusable link, or a restart after durable upload success before the edit boundary, shows **File uploaded · edit not sent**. A crash before the upload boundary reports no upload or edit sent. An unambiguous edit rejection reports the rejection and that the upload may remain accessible. Once edit dispatch may have occurred, missing durable acknowledgement means **May have been submitted**. A durable task ID resumes existing status reads. Recovery sends neither POST. For a new attempt, restage and require fresh Review and consent. Tell the owner to check provider history first when the edit outcome is uncertain and explain that a new upload can create another copy and incur charges.

For Poyo.ai, reserve the wallet interval before reading the starting balance and separately mark the upload dispatch boundary. If recovery establishes neither POST was dispatched, close the interval without a comparison. For a confirmed rejection or stored upload ending before edit, the live dispatcher closes the interval after its bounded after-balance read under the reviewed revision. A missing read leaves the comparison unavailable. When startup recovers a definite early exit, close its interval without a comparison or network call. An unresolved upload or edit keeps its wallet interval open across key revisions indefinitely. No upload reconciliation or settlement deadline is documented. Confirmed edit outcomes follow the existing tracking rules. Jobs keeps upload cost unknown alongside any known edit estimate and task charge on both providers. Upload settlement timing is unknown. The wallet difference describes account movement during the observation interval.

## Attached-file copy

Failures never mention the opt-out.

- Neutral status: "The staged file is no longer available." · "The staged file expired."
- Off status: "Checking the file…", then "File checked · Not cleaned." Alt text "Attached file"; no survival list.
- Off details: "Metadata removal is off in Settings. Siluet checks this file on this computer and sends it unchanged."
- Off Review: "**Not cleaned.** Metadata removal is off in Settings, so Siluet sends this file to {provider} unchanged, including any location, camera, authorship or AI-source metadata."
- Rotated original (hashed terms only; the slot shows **Not cleaned**): "Providers do not document camera orientation; the result may come back rotated."
- Settings switch **Remove metadata before upload**. On: "Siluet sends only a cleaned private copy, without location, camera, authorship or AI-source tags. An embedded color profile stays; its creator, copyright and device fields can survive." Off: "Siluet sends each file exactly as attached, including that metadata. Files are still checked on this computer first." Both: "Changing this needs a new Review; jobs already queued keep the file they reviewed." Stale save: "Changed in another tab".
