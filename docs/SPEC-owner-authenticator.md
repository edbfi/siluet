# Owner authenticator and host recovery

Approved by the owner after council review.

The single loopback owner can add an authenticator after claim or in Settings → Security, use it at sign-in, and recover the existing studio after losing access. Password is the sole primary method in this module. [Owner access follow-up](SPEC-owner-access.md#follow-up-prs) · [D1 owner sign-in](decisions.md#owner-sign-in)

## Sign-in and Security

- Claim issues the owner session and closes /setup. Redirect a successful claim to the authenticated offer under Settings → Security for authenticator setup with an explicit **Skip for now** that opens the studio. Immediate setup requires reentering the password through the normal Security reauthentication flow. An ordinary successful sign-in opens the studio. With MFA off, verified primary credentials issue the existing owner session. With MFA on, they issue only a five-minute pending sign-in. Store a digest of the random browser proof, its purpose, canonical origin, owner, primary method and configuration revision, MFA revision and expiry. Deliver the token in a separate host-only HttpOnly cookie scoped to `/sign-in`, with the existing SameSite and scheme-derived Secure policy. The challenge permits only factor entry or cancel. The hook continues to deny private loads, media and mutations until a full session exists. Expiry, cancellation or replacement invalidates the pending sign-in. Use monotonic deadlines for pending sign-in and Security proofs and invalidate both on restart.
- A fresh sign-in through an enabled primary method authorizes each Security change. Require the current TOTP or an unused recovery code if MFA is on. For enrollment and replacement, bind a five-minute, single-use authorization to the initiating live owner session, canonical origin, exact action and candidate, and the current primary and MFA revisions. A password-only or previously signed-in session is insufficient when MFA is on. For enrollment and replacement, consume the current factor when granting the candidate-bound authorization and consume that authorization when committing the change. For disable and recovery-code regeneration, verify fresh primary proof and consume the factor and apply the exact change in the same transaction, so a failed change preserves the last recovery code. A rollback at either step preserves that step’s unused proof.
- To enable or replace TOTP, create a fresh 20-byte seed with `randomBytes`. Reveal it only after reauthentication, as a locally rendered QR and selectable, unpadded Base32 text. Use `otpauth://totp`, issuer `Siluet`, and an account label with a short installation identifier. Use RFC 6238 with HMAC-SHA-1, six digits, 30-second steps and Unix epoch zero. Keep the candidate server-side and bound to the authorization, expiring with it and discarded on restart. Verify a code from the candidate before committing and count that step as used. Until commit, the existing factor policy stays active. Replacement revokes the old seed and codes. Turning off MFA revokes the seed and codes. Regeneration replaces the complete recovery set in one transaction and preserves the current seed and its used-step state. [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238.html) · [RFC 4226](https://www.rfc-editor.org/rfc/rfc4226.html) · [Google Authenticator URI format](https://github.com/google/google-authenticator/wiki/Key-Uri-Format) · [OTPAuth](https://github.com/hectorm/otpauth#usage) · [Local QR encoder](https://github.com/paulmillr/qr#encoding)
- Every committed Security change increments the security revision, invalidates all pending proofs, revokes other sessions and rotates the initiating session. Clear the initiating tab’s private draft without redirecting it. Deliver the one-time codes in the winning response and keep them readable until the owner leaves. Invalidate drafts in other tabs using a distinct Security-change signal, reserving the sign-out redirect for sign-out. Other browsers learn of revocation on their next protected request, which denies access and signals draft invalidation. A response to an obsolete session must leave the shared session cookie alone so delayed responses cannot clear a newer login. For future OIDC and LDAP, the same session-issuance boundary accepts only a server-verified proof for the singleton owner and its exact method configuration, then applies the current Siluet MFA policy. Provider claims alone cannot satisfy this factor. The external sign-in spec owns binding validation, method changes and the last-method check under D1.

## Verification and storage

- A TOTP field takes exactly six ASCII digits and preserves leading zeroes. Snapshot server time and generate expected values for the current, previous and next steps with a maintained OTPAuth release pinned under Bun. Compare fixed-length values in constant time. Reject ambiguous matches and steps at or below a persisted per-factor high-water mark. A clock rollback cannot reset the mark. Guide the owner to check device time and try the next unused code. [RFC 6238, security and resynchronization](https://www.rfc-editor.org/rfc/rfc6238.html#section-5) · [OTPAuth TOTP API](https://hectorm.github.io/otpauth/classes/TOTP.html#generate) · [Bun crypto](https://bun.com/reference/node/crypto)
- Reserve attempts durably and atomically before checking either code type against a valid pending proof. Share one installation-wide budget across sign-in, reauthentication and enrollment. Limit failures to five per rolling five minutes and 100 consecutively. Count in-flight reservations against both limits regardless of age. Record malformed and replayed submissions and rolled-back checks as failures. On startup, finalize abandoned reservations as failures. Age the rolling window using monotonic elapsed time anchored to the last persisted budget time. Wall-clock changes and time while stopped earn no credit. A committed factor success releases its reservation and resets the streak of completed failures, leaving other reservations charged. A candidate can reset the streak only when it becomes the first active factor. Keep the existing primary throttle. Return a retry time for temporary throttling and direct the owner to host recovery when the 100th consecutive failure locks further factor checks. [RFC 4226, throttling](https://www.rfc-editor.org/rfc/rfc4226.html#section-7.3) · [NIST SP 800-63B, rate limiting](https://pages.nist.gov/800-63-4/sp800-63b.html#rate-limiting)
- Generate ten independent 128-bit recovery codes on enable, replacement or regeneration. Group uppercase hex for display and accept either its grouped or ungrouped form, case-insensitively. Store only domain-separated SHA-256 digests bound to the installation and set ID. Compare fixed-length digests. Each code substitutes for the factor after fresh primary verification and succeeds once across sign-in and Security. Display the newly issued codes only in the winning response, with their remaining count available later. If that response is lost, use fresh proof to regenerate. Show the consequence of using the final code. [NIST SP 800-63B, look-up secrets](https://pages.nist.gov/800-63-4/sp800-63b.html#look-up-secrets)
- Migrate existing owners to MFA off and preserve valid sessions. Use explicit security state so inconsistent factor or recovery-set records fail closed. Authenticate the seed with AES-256-GCM using a fresh 96-bit nonce and 128-bit tag. Bind the envelope version, installation ID, owner ID and factor ID as associated data. Generate a separate 32-byte key per factor. Store it under a unique factor-derived filename in private owner data, separate from the database and provider key. Before reading an active key, require a private, singly linked regular file with verified ownership and permissions, including ACLs on Windows. Reject symlinks and reparse points, and bind verification and reading to the same file identity. On Windows open the file with reparse-point inspection, deny concurrent write and delete sharing and check its attributes and link count. Request READ_CONTROL, obtain its owner and DACL through GetSecurityInfo and read through that same handle. Implement the Windows operations in a small checked-in C# helper using documented Win32 P/Invoke and captured Win32 errors. Compile it at Windows build time with the .NET Framework C# compiler and ship it beside the trusted application build. Use private, bounded binary stdin and stdout to transport key bytes. Keep secrets out of arguments, environment and diagnostics. Treat helper launch or protocol failure as temporary. Run the actual helper on native Windows CI for both read and publication. [Windows handle-based access checks](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-getsecurityinfo) Create the new key exclusively, verify its permissions before writing, and finish the following platform publication steps before committing the active reference. On POSIX sync the new file and its directory before activation. On Windows flush and close the exclusive private temporary file, then publish to its unique final name on the same volume using MoveFileExW with WRITE_THROUGH and without replacement. Abort activation on a failed flush or publication. Qualify restart behavior with fault injection at each boundary. Windows does not document power-loss durability of the final directory entry for this same-volume rename. An abrupt machine restart may leave the database referencing a missing key even after activation succeeded. Accept host recovery as the fallback on that platform. Disclose this before activation with the stopped-service recovery command. On restart, verify the reference and refuse access when the key is missing. Cover that recovery with a restored database and a missing published key. Fault injection checks recovery behavior and does not establish hardware power-loss durability. [Windows file publication](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw) Retain the old referenced key until the replacement transaction is durable. Never replace a key path. A failed commit leaves the old factor usable. Clean up verified unused keys only, and preserve unrecognized entries. Backups made with the server stopped include the database, its referenced keys and the recovery lock sidecar. [NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final) · [Bun crypto](https://bun.com/reference/node/crypto) · [Windows reparse points](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-points)
- On startup, create or verify the sidecar and finish recognized installation migrations before the active-key check and before starting workers or accepting requests. Check the active key and authenticated ciphertext before serving normal access and on sign-in or Security proof with MFA enabled. Confirmed absence, an observed ownership, permission or file-identity violation, a mismatched key or a failed authentication tag sets persistent recovery-required state if the checked factor and revision are still current. The request gate immediately refuses active sessions as well as new sign-ins on every protected page, media route and mutation and directs the operator to host recovery. A temporary I/O, sharing, resource or ACL-inspection error closes access until a successful recheck and offers Retry. Preserve factors and recovery state on inconclusive checks. Recovery codes cannot bypass a key failure. In an immediate Drizzle transaction, recheck policy and revisions for every session or proof issued, including password-only sign-in racing enrollment. Recheck the pending proof, its expiry and the initiating session where required. Conditionally advance the step or consume the recovery digest in the same transaction as the associated proof, session or setting change. Issue cookies and display generated codes only after commit. A second request with the same proof, step or recovery code loses even across tabs, connections or restart. [Drizzle transactions](https://orm.drizzle.team/docs/transactions) · [Turso transactions](https://github.com/tursodatabase/turso/blob/v0.8.3/docs/manual.md#transactions)

## Stopped-service recovery

Run `bun run owner:recover` as the OS account that owns the installation, using the same production data-directory resolution as startup. Use a dedicated, private `bun:sqlite` sidecar at one stable path in the canonical local data directory. Use rollback journal mode (`DELETE`) with a zero busy timeout. Before opening Turso, the built or dev server starts an explicit read transaction and reads the sidecar’s sentinel table to acquire a shared lock. Recovery opens the existing sidecar, takes `BEGIN EXCLUSIVE` and verifies the sentinel before opening Turso. Preserve Turso’s single-process file locking to reject a second server. Keep a strong reference to the dedicated connection and hold its transaction through the last Turso storage close, including startup failure and shutdown. Avoid other file handles to the sidecar during that interval. The OS releases locks when the process exits, including after forced termination. Refuse lock contention immediately. Never unlink, replace or steal the sidecar. [Bun SQLite](https://bun.com/docs/runtime/sqlite) · [SQLite transactions](https://sqlite.org/lang_transaction.html) · [SQLite file locking caveats](https://sqlite.org/howtocorrupt.html#locking) · [Turso process access](https://github.com/tursodatabase/turso/blob/v0.8.3/docs/manual.md#limitations)

Only startup may create the sidecar, using exclusive file creation. Before opening it, verify it and any bootstrap journal are private, singly linked regular files without symlinks or reparse points. Initialize the sentinel in an exclusive transaction after checking that the sidecar is still empty. SQLite handles interrupted bootstrap through its rollback journal. Refuse unsafe files, unexpected schema or a different journal mode. Exclude only the verified sidecar from the fresh-installation check. Recovery requires an initialized sidecar and opens both databases in existing-file mode. If a known older installation or complete restore lacks the sidecar or needs migration, instruct the operator to start the installed version once, stop it, then run recovery. Startup reaches sidecar initialization and migration even with an unusable active key.

Under the lock, verify the existing private directory, matching installation marker and database, a recognized current schema and the claimed singleton owner. Recovery neither initializes nor migrates storage or starts workers. On startup and recovery the Windows generic ACL scan defers filenames in the reserved factor-key namespace, including inactive keys left by recovery. Check the active key through the stricter checks above and keep the directory and other entries under their existing policies. Recovery leaves factor keys untouched and never opens their contents. Refuse a busy, unclaimed, incomplete, damaged or unrecognized installation with redacted guidance.

Prompt for and confirm a new password on an interactive terminal with echo off. Reject redirected input. Restore the saved terminal mode on normal exit, errors and handled cancellation. Forced termination cannot run restoration code, so give the operator platform-specific guidance for restoring echo. Validate and hash with the existing password policy and asynchronous Bun Argon2id. In one transaction update the same owner’s password and advance the security revision, clear recovery-required state, active and pending factors, codes and both throttles, revoke sessions and proofs, and suspend any future external bindings until reverified. Update the existing database in place and leave the marker, key files, provider credentials, jobs, Gallery metadata and media intact. After commit, restart and sign in with the new password. [Bun terminal input](https://bun.com/reference/node/tty/ReadStream/setRawMode) · [Windows console mode](https://learn.microsoft.com/en-us/windows/console/setconsolemode) · [Bun password hashing](https://bun.com/docs/runtime/hashing#bun-password)

## UI and acceptance

Keep route actions thin, orchestration under `src/lib/server/services/owner/` and state changes behind focused Drizzle functions. Use the existing owner form and Panda styling with labeled fields, paste and `autocomplete="one-time-code"` for TOTP, manual setup alongside QR, keyboard focus on the new heading or error, and announced errors and status changes. Verify the built flow on narrow screens, in both themes and with JavaScript disabled. Keep secrets out of URLs, diagnostics, echoed values and browser storage. Send `no-store` on auth and Security responses, with no third-party requests. Serve seed and recovery material only in their authorized responses. Refresh, form replay and history refetch cannot retrieve the recovery list. With scripting available, clear secret markup when leaving the view so a browser history snapshot cannot reveal it. [WCAG accessible authentication](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html) · [Chrome history caching](https://developer.chrome.com/docs/web-platform/bfcache-ccns)

- Exercise the built loopback server with a temporary installation and locally generated fixtures. Claim and skip, then enroll from Security. Separately, prove immediate enrollment requires password reentry. Verify QR and manual entry encode the same seed. Sign out, prove private routes reject partial sign-in, and complete TOTP and recovery sign-in separately. Verify replacement, regeneration and disable revoke their predecessors. Verify the initiating tab retains its one-time codes through session rotation and rollback preserves the last recovery code on a failed disable or regeneration. Delay an old-cookie rejection until after the rotated session and one-time codes arrive. Verify the codes stay readable and a new protected request succeeds. Check draft invalidation in same-browser tabs and stale-session rejection on another browser’s next protected request.
- Cover RFC 6238 Appendix B vectors, the production profile, window boundaries, concurrent and restarted replay, and clock changes. Verify concurrent reservations cannot exceed either limit, interrupted checks stay charged and the 100th consecutive failure requires host recovery across restart. Race password-only sign-in with activation. Assert that failing to insert a session rolls back factor consumption and failing activation leaves the previous state usable.
- Require native Linux, macOS and Windows CI for startup and recovery. Test contention in both directions, including a server on another port, simultaneous startup, interrupted sidecar initialization and forced process exit. Check that the stable file survives and can be locked again after exit. Exercise the actual command under a PTY or Windows pseudoconsole. Verify both password entries stay out of terminal output, normal and handled exits restore terminal mode, piped input is refused, and interrupted recovery preserves pre-commit state. [Bun terminal tests](https://bun.com/docs/runtime/child-process#terminal-pty-support)
- Inject a failure before and after each key publication and database activation boundary. Exercise temporary I/O or ACL-inspection failure followed by a successful retry, and permanent absence, unsafe permissions or invalid ciphertext requiring recovery. Test a private page, media and a mutation from an existing session after factor-key failure is detected. Recover with missing and unsafe keys, including a loose active-key ACL on Windows. Exhaust both authentication budgets, recover and sign in immediately. Cover mismatched markers, missing or damaged storage, redaction and rollback. After recovery, verify that the old password, sessions, proofs and factors fail, and that representative jobs, provider credentials and saved media still open. Verify no replacement of pre-existing files and no creation of an installation in refused cases. Run the [local development checks](../README.md#development).
