# Browser key sessions

Approved after council review ([D1](decisions.md#browser-credential)); key rotation approved after five council rounds (2026-11-26).

Replaces the cookies of [Owner access](SPEC-owner-access.md) and [Owner authenticator](SPEC-owner-authenticator.md), which browsers send to every port: a browser proves it holds a key only Siluet's exact origin can use.

**Installation ID.** One `transformPageChunk` on every `resolve()` fills `<meta name="siluet-installation">` in page and 404 shells. Client `init` checks it (UUID v4) before storage or signing, failing closed.

**Browser key.** IndexedDB `siluet-owner`, keyed by installation ID, holds only `{key, spki}`: a non-extractable ECDSA P-256 key, replaced only by a committed claim or sign-in. Before each candidate, `/setup` and `/sign-in` check `isSecureContext`, `crypto.subtle` and that IndexedDB opens, then sign a test message with the candidate; failure names the address and browser. A commit calls `navigator.storage.persist()`. Cleared site data, another port or address family: signed out.

**Key rotation.** Every claim and sign-in signs with a new candidate key held only in that tab's memory. The tab's first read of the stored record gives the expected SPKI (absent if none or malformed) and the base (the record, only if it signs a test message). Retries, the lost-answer `resume` and the factor step reuse the candidate and base. The attempt holds the submitted fields in memory beside them, cleared when the candidate is dropped, refused or committed, when sign-in settles with a pending proof, and on `pagehide`. A submit, retry or factor step that finds another stored SPKI drops both and loads `/`, as a refused commit does: it joins a live session (clearing the `siluet-sign-in-pending` marker), else `/sign-in` shows "Sign-in restarted" if a factor step was pending. After a lost answer it first resumes the candidate: a session supplies the login ID it signs out (best effort); a 401 leaves nothing to sign out, and a later commit ends at the idle limit. A tab with its own claim, sign-in or factor request, or its lost-answer `resume` or resend, in flight acts on any stored-SPKI change it finds (a notice, focus, visibility or `pageshow` check) only after that request settles. Sign-in and factor add `replaces: {key, signature}` for a base: the base key signs the same purpose and nonce, bound to `replaces:<candidate SPKI>`; the nonce is spent once for both. Claim and a sign-in without a base send none; `/owner/claim` refuses any. Both signatures verify before access, database or password work; a non-object `replaces`, a bad signature or one equal to `key` is 403, after the nonce is spent. A pending proof records no base (no migration): a factor step omitting `replaces` is a client bug that keeps the base's session, and naming a base still needs its private key. The transaction that issues the candidate's session also replaces the base key's session, retiring its bearers, staged work and pending sign-in proofs in that turn; issuing a pending proof retires nothing. First commit wins: in the transaction that would issue a session or proof, `/owner/sign-in` refuses a key that already has a live session with 409 `session-live`. A newer pending proof replaces the key's earlier one, so the last proof wins. On success the tab commits in one readwrite transaction: it puts the candidate while the stored SPKI is still the expected one (overwriting an unchanged record that cannot sign) and refuses otherwise, then binds and broadcasts once the transaction completes. Factor completion commits the sign-in's candidate; cancel sends no `replaces`, retires nothing and drops both. Security changes keep the key and login ID; `resume`, cancel and sign-out never rotate. `pagehide` invalidates the attempt through key generation, answer handling and the start of the commit transaction, so later steps do nothing. A back/forward-cache return without a candidate clears any factor proof; if a commit had begun, it re-reads the stored key and checks. It shows "Sign-in restarted" only if a factor proof was pending and no live session was joined.

- Refused, 403, 429 or access error: nothing is stored, and the base keeps its session, if any. A refusal is a 403 or 409 with a `{message, reason}` body, mapped the same for a first answer and a resend: `invalid-claim` shows the claim-token message; `invalid-code` keeps the proof, candidate and base for a new code; `stale-proof` and any other or missing `reason` drop both, clear any pending proof and return to the sign-in form with "Sign-in restarted" for a factor step, or show the message. A 429 or a retryable access error is not a refusal: it keeps everything and offers Retry.
- Network failure or unreadable answer: the tab first sends `resume` signed by the candidate. A session means the request committed: the tab commits, binds and broadcasts as if answered. A 401 alone is not proof, since the original may still be running (claim hashes the password before its transaction; the claim token and pending proof are spent only in the committing one): the tab resends the held fields once per attempt, for claim, sign-in and factor alike, on the same candidate and base. Only one can commit: a late original sign-in gets `session-live`, a late claim or factor finds its token or proof spent. A late original's pending proof replaces the resend's, so the factor step gets `stale-proof` and restarts (accepted). After any refused resend the tab resumes once more: a session commits; a 401 applies the resend's own refusal as mapped above. A 429 or retryable access error on the resend skips that step and offers Retry, keeping everything. A second lost answer, or a retryable result that is neither a session nor a 401, keeps the candidate, base, fields and any pending proof and offers Retry, which resumes first and resends the held fields only on a 401; the credential inputs stay disabled while it is offered. A non-retryable access error (`recoveryRequired`, `retry: false`) shows its host-recovery message instead.
- Tab closed or crashed before the commit: the base stays stored. If the server committed, the lost candidate's session is unusable and ends at the idle limit (no purge: purging by base would end a winner's session), and the base has no session, so the browser is signed out.
- Commit refused, because another tab committed first (two tabs signing in at once, or a notice deferred while the tab's own request was in flight): the tab signs out the login ID its answer gave with the candidate (best effort), drops both and loads `/`. Each `replaces` named the same base, so the stored key's session survives; a failed sign-out leaves the abandoned session to the idle limit.
- Commit write failure: the same sign-out, then the key message; a factor step's pending proof is cleared. The browser stays signed out.
- After rotation the base key's `resume` is "Session gone" and its sign-out finds no session. Its retired bearers get `invalid_token`; other tabs renew and re-read the key. A tab handling that 401 after the commit takes "Replaced key" to "Other ID" without a sign-out (with codes: "changed"); one handling it before the commit is signed out to `/sign-in`, which loads `/` once the new key commits (accepted gap). A tab on `/sign-in` or `/setup`, or in the codes hold, that gets a commit notice or revalidates and finds a stored SPKI other than the one it last resumed or checked runs a signed `resume` with it; the codes hold does so even while a destination is pending. `/sign-in` and `/setup` load `/` only on a session result, else stay; a tab holding its own candidate takes the submit-time "another stored SPKI" path. The codes hold, resuming the new key into a live session, marks the codes "changed" unless they are already "replaced" ("do not keep these"), which sticks, and replaces a deferred `/sign-in` destination with `/settings/security`; codes stay until Done. Pinned requests keep their session ID.

Why: a sign-out followed by a sign-in cuts off a copy of the stored key, as in a copied profile or backup; the copy loses the old session and cannot sign for the new key. Rotation does not end a session the copy shares while it lives, stop code running in Siluet's origin, or protect a password or second factor.

**Challenges.** `POST /owner/challenge {purpose}` returns a 256-bit nonce, single use, 60 s monotonic, lost on restart. `resume`: 64 outstanding (oldest dropped), 120 per minute; others 16 and 30; then 429. Browsers sign LF-joined `siluet-browser-key/1`, purpose, canonical origin, installation ID, binding, nonce (ECDSA SHA-256, 64-byte P1363). Binding: empty for claim and sign-in, the pending proof's digest for `factor`, the SPKI for `resume`, the login ID for `sign-out`, `replaces:<candidate SPKI>` for `replaces`. Signed requests send `key` (SPKI, re-encoding byte-identically). Endpoints consume the nonce and verify before access, database or password work; failure is 403.

**Sessions.** One per key: an internal random digest (never sent), the unique public key, unique random 128-bit session and login IDs (not secret), creation and last activity (7-day idle, 30-day limits). `/owner/claim` and `/owner/sign-in` verify `{key, nonce, signature}`, then token, throttle, password. Without MFA the transaction issues the key's session and replaces its base's (retiring bearers, staged work, proofs). With MFA, sign-in returns a five-minute pending proof replacing only that key's sign-in proof; `/owner/factor {proof, key, replaces?, code | cancel, nonce, signature}` acts only on it; another key spends no factor budget. Reload shows "Sign-in restarted". Claim, sign-in and factor success return `{bearer, sessionId, loginId}`, both IDs new; only a Security change keeps a login ID. Their 403 and 409 bodies are `{message, reason}`, `reason` one of `invalid-signature` (including `replaces`), `invalid-claim`, `invalid-login`, `stale-proof`, `invalid-code` and `session-live`; a factor step with no proof answers `stale-proof`; other refusals (400, 429, the hook's checks) carry none; the client branches on `reason`, never on message text.

**Bearers.** 256 random bits, ten minutes monotonic, in tab memory; the server maps digests to sessions, 64 per session (oldest evicted), registered in the `install.use` turn of the commit and retirement (claim: its `use` callback after commit) or the read, so revocation drops them in order. `POST /owner/resume {key, previous?, nonce, signature}`: no or expired session is "session gone", 401 `{message, location}` (`/setup` before claim, `/sign-in` after); recovery-required or unavailable storage gets the access JSON; success returns `{bearer, sessionId, loginId}` and retires the same session's `previous`. `GET /owner/session` (bearer, read-only, not `checkSession`) returns the live `{sessionId, loginId}` or the access JSON and issues nothing. Neither touches last activity.

**Client.** `init` wraps SvelteKit's `window.fetch`, setting `Authorization: Bearer` and `credentials: "omit"` on the caller's same-origin `init` (keeping `__sveltekit_fetch__`). A keyed tab binds to a session ID on its first `resume`, run cold before private requests or `/sign-in` data. Each private request, draft, staging, retry or cleanup captures that ID at creation and is sent (or resent once after a hook `invalid_token`) only with that session's live bearer. A live bearer sends synchronously (`pagehide` keepalive). Renewal is single-flight, settles when `resume` returns and re-reads the key. A route's own 401 is final. Wrapper failures are `TypeError`; `AbortError` passes. A keyless tab sends no bearer, following the hook's `location` or access JSON. A signed-out tab ("Session gone", vanished key, sign-out) fails private requests until sign-in or a document load, sending `/sign-in` and `/setup` data bare. Data promises stay pending only while the wrapper navigates or defers a load.

Result | Tab | Pinned request
---|---|---
Bound ID | Keep | Sent or resent once
Other ID | Document load of the current or target URL; with codes, held for Done | `TypeError`
Session gone, missing key | Unbind, drop drafts, open the response's `location` (`/sign-in` without one; not from `/sign-in`, `/setup`); with codes, held for Done | Action: `{type:"redirect",status:303,location}` unsent; `/sign-in`, `/setup` data without bearer; else `location.assign`
Replaced key | Its `resume` result's row; "Session gone" from a key no longer stored resumes once more with the stored one | As that row
403 | Fresh challenge, `resume` once | Waits
Second 403, 5xx, 429, network | Stays bound | `TypeError`; `/sign-in`, `/setup` data without bearer
Access error | Stays bound; `recoveryRequired` drops drafts | Access JSON, or action `{type:"error"}`
Second `invalid_token` | Stays bound | `TypeError`

Responses apply effects only if `remountKey` is unchanged since sent. Otherwise they are dropped, except a recovery-required answer, which reaches its caller without effects, and a Security response, which goes to its settlement. A request body is applied once and cloned for each send.

**Revalidation and notices.** On `focus`, visible `visibilitychange` and `pageshow` a tab checks (`GET /owner/session` with a live bearer, else `resume`; single-flight, recheck bit) and the table applies; none runs while a destination is pending or loading, except the codes hold's check of a newly stored key. Claim, sign-in, factor, Security and sign-out post `{id, kind, sessionId | null}` on `BroadcastChannel("siluet-owner-<installation>")` and localStorage. Notices are hints: a tab on that ID ignores one; a hidden tab drops its bearer (kept as `previous`) and checks when visible; a failed check stays pending; `/sign-in` and `/setup` never reload (for a new stored key, see Key rotation).

**Security changes.** The transaction re-checks the initiating session and revisions, replacing every session with the successor (same key and login ID, new session ID). The response carries `{sessionId, codes}`, the bearer in a `no-store` header the wrapper strips. Submit is disabled while pending. The POST never waits (a preflight or retry meeting another or no session fails it); "Other ID" or "Session gone" waits for the response. Settlement moves `codes` into the layer (not `page.form`), then the tab adopts the successor (bind, broadcast, `remountKey`+1, then `enhance`'s `update()`) if still bound to the start ID and no waited result disagrees (the latest waited one names it); otherwise only that row applies, announcing no dead successor. After the owner leaves, a response shows no codes and installs no bearer but broadcasts and checks. sessionStorage names candidates by proof digest; `?resume=<digest>` reopens one only for its live session, action and revisions within five minutes. `pagehide` clears a shown candidate, registering `/settings/security` (keeping `?offer`) as a lower-priority destination for a back/forward-cache return.

**Unread codes.** Only codes open it: the root `+layout.svelte` closes StudioShell's drawer and `showModal()`s an opaque `<dialog>` outside `{#key remountKey}`, routes and error pages (the top layer inerts the rest; overlays stay unportaled). It has `closedby="none"` where supported, a capture `keydown` listener blocks Escape while it is open, its `cancel` is prevented, backdrop clicks are ignored, a non-Done `close` reopens it while codes are held (clearing them unmounts it) and its `::backdrop` is opaque; autofocused Done reclaims focus after `update()`, `afterNavigate` and outside `focusin`. Nothing beneath is cancelled or closes it. Rows sent here drop drafts, retire the session and defer one document load (`/settings/security` for "Other ID", else the response's `location` or `/sign-in`); private requests wait at the wrapper. A later Security change (same login ID) marks the codes "do not keep these"; "Signed out" or a new login ID says they hold only if two-step sign-in is unchanged. Done consumes, then loads, any destination (reload if `location.href` at click, else `location.replace`); with none, a change submitted from a Security URL with `offer` continues to `/settings/files?offer` only while `location.href` still equals that submitting URL. `pagehide` clears codes and hold; the sole `pageshow` handler takes a pending destination atomically, loads it alike and checks nothing.

**Sign-out.** `POST /owner/sign-out {key, loginId, nonce, signature}` verifies, purges expired sessions, then revokes the key's session only if it carries that login ID: a rotated successor ends, a later sign-in does not. No session: success. Another login: 409. Results apply against the key and login ID taken when sign-out began, not a key read later. Before applying success, the tab re-reads the stored key: another key resumes and its result applies through the table, and joining a fresh session shows the 409 path's offer to sign it out. For "Other ID" the tab sets a single-use sessionStorage `siluet-sign-out-offer` naming the fresh session ID and loads `/`; the next document consumes it, showing the offer only on `/` bound to that ID, and a back/forward-cache restore clears it. With no other key, or on "Session gone", the tab unbinds, drops drafts, broadcasts and opens `/sign-in`. A 409 always applies: the tab checks and offers to sign the other login out, using the same flag when that check loads a document. A 403 retries once, then offers Retry.

**Admission.** Public: documents (non-data GET/HEAD of a `+page.svelte` route) and unmatched GET/HEAD as shells (`ssr = false`, meta, `<noscript>` notice; `/setup` 404 once claimed); `/healthz`; `/setup` data until claimed; `/sign-in` data (to `/setup` before claim, `/` with a valid bearer); `POST /owner/{challenge,claim,sign-in,factor,resume,sign-out}` (Origin, Host, 512 KiB checks; the hook skips `checkAccess`, which signed rows run after verifying). All else, `/owner/session` included, needs a bearer; public rows ignore invalid ones. A missing or dead bearer gets a `no-store` hook 401 (never 3xx) with `WWW-Authenticate: Bearer` (`error="invalid_token"` if sent): the redirect envelope for actions, else `{message, location}`. Access errors: static page for documents, `{message, retry, recoveryRequired}` for data (root `+error.svelte`, outside `StudioShell`), `{type:"error"}` for actions, JSON elsewhere.

**Pages and forms.** Home loads the username. POST forms `use:enhance` and apply `error`; the ToAPIs check sets or clears its feedback; setup and sign-in post JSON. Shells send COOP `same-origin`.

**Media.** Bearer-fetched blobs: 64 MiB per video, 32 MiB per image, 32,000,000 bytes per staged copy; type from the job's MIME. Per tab: four reads, 192 MiB, least recently visible evicted. Shown files keep one read. Downloads take at most three reads and 128 MiB, in click order, each waiting as pending for its share before it sends; with no download reading, the oldest takes the next free read. A remount or leaving drops waiting downloads. URLs revoke after 60 s or on unmount. CSP `media-src 'self' blob:`.

**Upgrade.** Documents expire this installation's legacy cookies at their paths (`siluet_<id>`, `siluet_signout_<port>`, `siluet_security_<port>` at `/`; `siluet_<id>_pending[_<hex64>]` at `/sign-in`; `siluet_<id>_setup_<hex64>_<hex64>` at `/settings/security`) without reading them. One append-only migration deletes all owner proofs, recreates `session` with key and ID columns, adds `owner_proof.public_key` and keeps other data. Rotation needs no migration: the record and tables keep their shape, and an earlier key rotates at its next sign-in.

**Out of scope.** A process taking Siluet's origin while stopped; code running as the owner.

**Acceptance.** Built-app journeys on Linux (Chromium, Firefox) and macOS (three engines); another loopback port gets and replays nothing; an agent-browser check in Chrome stands in for real Safari (owner, 2026-11-26; passed on `23efde9`, video playback not exercised).

Its built-app journeys run in Chromium, Firefox and macOS WebKit. They claim and sign in through the forms, with and without the factor step, or a helper that rotates and sends `replaces` as they do; keep the old key for stale-key checks by copying it into a test-owned store before rotation; order server commits with `page.route` holds; lose answers by letting the request commit (`route.fetch()`) and then aborting it; inject IndexedDB `put` failures; and assert `pageshow.persisted` where an engine really restores from the back/forward cache, else dispatch the persisted lifecycle events as tab-sessions does.

- Claim and sign-in, with and without the factor step, store a new SPKI, and the old key's `resume` gets 401. Sign-out then sign-in leaves the old key nothing. A Security change keeps the SPKI.
- A claim, and a sign-in without a base, send no `replaces` and are accepted.
- A refused sign-in, and a reload or back/forward-cache return mid-factor, keep the stored record; the return shows "Sign-in restarted" only when a factor proof was pending, also after a commit `pagehide` interrupted left no live session.
- A lost claim, password-only sign-in and factor completion, each aborted after the server committed, reach the new session through the candidate's `resume` without re-entry. A lost sign-in whose original lands after its resend committed gets `session-live` and leaves the resend's session bound. A tab closed with the answer held leaves the old record and a signed-out browser.
- Two tabs submitting at once leave one stored key and one live session, which both tabs reach; with the loser's sign-out failing, the winner still survives. With the loser's request held until the winner's notice arrives, or until a `focus` check finds the winner's key, the loser acts only after its answer, is refused at commit and signs that login out.
- A stored record that cannot sign is overwritten. One another tab replaced before submit sends the submitting tab to `/`.
- A failing IndexedDB put shows the key message and clears a factor step's proof; when the cleanup sign-out succeeds, the candidate has no live session. With that sign-out failing too, the local record is unchanged and the abandoned session ends at the idle limit.
- With the answer held until each sibling has handled the old key's 401, a bound tab is signed out to `/sign-in` and loads `/` once the new key commits, a `/sign-in` tab loads `/`, and shown codes stay until Done, marked "changed", with Done loading `/settings/security`. A bound tab handling that 401 after the commit reaches the new session without `/sign-in`. A `/setup` tab during another tab's claim loads `/`.
- Both late-sign-out journeys in tab-sessions are rewritten: a held 200 landing after another tab's rotation, and a sign-out by the old key sent after it (200, no session), each re-read the key and join the fresh session directly, without `/sign-in`, offering to sign it out after the document load. One naming the old login, signed by the new key, gets 409 and makes the same offer, with notices to the tab under test delayed until it lands. The fresh login survives all three.
- Every browser test signs in through `signInOwner`, which becomes the rotating helper: it takes the code (or TOTP secret), runs the factor step with the candidate and `replaces`, and stores the key only after the commit, so the direct `signedInPage(..., "factor")` calls go away; `claimOwner` likewise holds its candidate and stores it only on success, so callers whose stored key is live no longer meet `session-live`; that includes the edit-studio `newSession` fixture, the tab-sessions journeys where another tab signs in (codes shown before it, a Security change after it, a cache restore after leaving for its session, and Done after Back moved the URL) and the authenticator journeys. All pass with rotation, the first still marking the codes "changed" and loading `/settings/security` on Done.
- The key-persistence, restart, back/forward-cache and cross-port journeys pass with rotation.
