# Claiming Siluet and signing in

Design proposal within Siluet’s [single-creator, loopback boundary](../decisions.md). The operator who can read the local server terminal claims one creator account. That creator controls saved media, paid requests and provider credentials. The account starts with local password sign-in. After onboarding, the owner can use local password, OpenID Connect (OIDC) and direct LDAP in any nonempty combination. Each method opens the same owner account. The current production foundation provides only a status page and health endpoint.

## First run and everyday use

1. **Claim this studio.** An unclaimed installation prints a random single-use bootstrap token and the local setup address to its operator terminal. Show the token separately from the URL. Use a short expiry (proposed 15 minutes), rotate on restart, keep the token in memory and exclude it from browser responses, application logs and diagnostics. Anyone with access to the terminal output can claim the instance. The browser prompts for the token, username and password. Check the token before expensive password work and throttle attempts.
2. **Create the owner.** Hash the password server-side using Bun’s asynchronous Argon2id. Permit long passphrases, paste and password managers. Create the sole owner, claimed state and first session in one transaction, enforcing uniqueness in the database. Competing or repeated claims can produce only one owner. Recover cleanly after rollback. On the next boot, an existing owner closes the claim route. An unreadable or partially restored installation must surface a storage error rather than reopen setup.
3. **Secure your sign-in.** Offer optional authenticator-app TOTP after claim, with a Skip action. Also offer it later under Settings → Security. Generate the QR locally, activate only after a verification code succeeds, and show single-use recovery codes once. When enabled, require the Siluet factor after any first factor, including OIDC and LDAP, before granting a full session or accepting a sign-in configuration proof. Consume accepted time steps and recovery codes atomically. A recovery code replaces the TOTP challenge after a valid first factor. [TOTP standard](https://www.rfc-editor.org/rfc/rfc6238.html)
4. **Connect media providers** or explore the studio without a media key. Show only enabled methods on the sign-in page. Label the local password form and directory login form separately and submit each to its own handler. OIDC starts an explicit browser redirect. If an external method is unavailable, report the failure and let the owner choose another enabled method. Local sign-in works offline while enabled.

Obzorarr prints a new in-memory token every 15 minutes until claim and separates claim from operator recovery. Siluet can follow this behavior with its own routes, storage and tests. [Obzorarr setup at the inspected revision](https://github.com/edbfi/obzorarr/blob/418a0d0/docs/SPEC-setup.md) · [Obzorarr sign-in](https://github.com/edbfi/obzorarr/blob/418a0d0/docs/SPEC-sign-in.md)

## Settings → Security

Manage local password, OIDC and direct LDAP independently after onboarding. Show which methods are enabled and explain the effect of disabling one before the owner confirms. Opening Security, editing fields and selecting a preset stay offline. Identity-provider calls begin with an explicit test, sign-in or reauthentication.

### Test, link and change methods

1. **Authorize the change.** Start from an authenticated owner session and reauthenticate using an active linked method, including Siluet MFA when enabled. Use the local password for this step only when the owner chooses an enabled local method. A signed-in browser session by itself grants no authority to change sign-in methods.
2. **Verify the candidate.** For OIDC, complete the production authorization-code flow. For LDAP, search and bind through the production LDAP sign-in path. Confirm the returned identity explicitly. Exercise owner mapping and Siluet MFA through the same checks used at sign-in. Treat a new binding as pending until the explicit confirmation commits it. An existing binding must resolve to the same owner before it can serve as proof. Candidate flows grant no general studio access before activation. Keep the prior methods available if the test, confirmation or save fails.
3. **Prove a method that will remain.** Disabling a method, or replacing one so its existing binding will cease to work, requires fresh end-to-end sign-in proof for a method in the resulting configuration. For local-password disable, require this proof from a linked OIDC or LDAP method. A verified replacement can be linked in the same change with fresh proof for its exact configuration. A discovery check, a directory search, a previous test or an existing session cannot authorize removal. A current-method reauthentication can also serve as the surviving-method proof when its method and configuration will remain active.
4. **Commit the change atomically.** Use short-lived, single-use server-side proofs bound to the owner, initiating browser session, exact action and target, current security revision and applicable method configuration or candidate revision. In a transaction, recheck these bindings, the proof’s expiry and the resulting set of enabled, verified methods. Consume the proofs, apply the change, advance the revision and revoke affected sessions together. Serialize changes to the owner’s sign-in settings so a concurrent request using the previous revision must start again. Check the current method and revision before issuing a session from any in-flight sign-in. If the proof expires, the candidate changes or the transaction fails, ask the owner to repeat verification as needed and keep the previously committed methods.

For fresh OIDC proof, request reauthentication with `max_age=0`. Check `auth_time` in the validated signed ID token against the challenge start and the proof’s freshness window with bounded clock skew. A new token’s issue time or a fresh callback alone establishes no authentication time. If the provider cannot prove freshness, use an independently verified active method that qualifies for the action or use explicit host recovery to restore an active local method. For LDAP, use a new user bind and verify the bound directory identity. [OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html#AuthRequest)

### Local password off and on

On switching to external-only sign-in, delete the stored local password verifier, disable the local password endpoint and revoke every password-derived session as part of the commit. Clear the owner’s previous sessions on a method removal or replacement. The initiating browser can continue with a new session derived from the fresh proof for a surviving method, or sign in again with an enabled method. The owner ID, gallery, provider credentials, jobs and billing records carry through the switch.

To turn local sign-in on again, prove control of an active method with fresh authentication and enabled MFA, then set a new local password. A lost factor or upstream outage that leaves no usable method requires explicit host recovery. External sign-in failure never invokes local password verification, enables a disabled method or makes a retired password usable.

### OpenID Connect

Choose **Tinyauth**, **Authelia**, **authentik** or **Custom OIDC**. Each preset uses the same OpenID Connect relying party. Show a copyable exact callback URL derived from the configured local origin, the provider’s client-registration instructions, issuer and client ID fields, and a masked secret input. **Test and link** starts the owner-initiated round trip.

| Preset | What Siluet can help the operator do |
| --- | --- |
| Tinyauth first | Copy the documented command with Siluet’s client name, e.g. `tinyauth oidc create siluet`, then register the resulting client and exact trusted redirect URI on the Tinyauth host. The guide supports a client-secret file and an HTTPS issuer. Tinyauth added PKCE in v5.0.7 and lists `max_age` support in v5.1.0. Its subject derives from the username and client ID. Renaming or changing the client ID requires explicit relinking. Reassigning the original username under the same client can give the new person the owner’s subject. Reserve the linked username against reuse in the identity system and remove the old binding before retiring that username. If the operator cannot guarantee this, choose an issuer with a non-reassignable subject. [OIDC server and registration guide](https://tinyauth.app/docs/guides/oidc/) · [PKCE release notes](https://tinyauth.app/docs/reference/changelog/#v507) · [Reauthentication release notes](https://tinyauth.app/docs/reference/changelog/#v510) |
| Authelia | Show a confidential-client configuration template with placeholders, the exact callback, authorization-code grant and S256 PKCE. Use the provider’s documented secret-handling procedure. An LDAP-backed Authelia deployment can authenticate the creator through OIDC. [Client configuration](https://www.authelia.com/configuration/identity-providers/openid-connect/clients/) · [LDAP backend](https://www.authelia.com/configuration/first-factor/ldap/) |
| authentik | Link the admin to the application/provider wizard. Select OAuth2/OpenID, a confidential client, an explicit strict redirect and a signing key. Keep the opaque subject mode based on the user’s hashed ID. Show where to copy the application-specific discovery URL. LDAP can back authentik, and an LDAP Provider with an Outpost serves clients that speak LDAP. [OIDC provider](https://docs.goauthentik.io/add-secure-apps/providers/oauth2/) · [Default subject mode](https://docs.goauthentik.io/add-secure-apps/providers/scim/#oauthoidc) · [LDAP source](https://docs.goauthentik.io/users-sources/sources/protocols/ldap/) · [LDAP provider](https://docs.goauthentik.io/add-secure-apps/providers/ldap/) |

The guide buttons copy nonsecret settings or open official docs on request. Client registration and any required restart happen on the operator’s identity server. Use only the registered client’s credentials in Siluet. Confirm each recipe against a pinned, patched, disposable provider instance before advertising compatibility. Verify the exact issuer, client ID, callback origin and URI, certificate trust, stable subject behavior, signing keys, S256 PKCE and signed reauthentication timestamp on the tested release.

### Direct LDAP

Configure a directory endpoint, TLS trust, search base, login attribute and least-privileged service bind that can read the owner entry and its identifier. Use certificate- and hostname-validated LDAPS or required StartTLS before sending credentials. Scope the search, escape input as LDAP filter values and bound its time, size and result count. Require exactly one eligible entry with a single immutable ID. Use the returned entry DN for a separate user bind with a nonempty password. Verify the authenticated entry’s immutable ID and reject any mismatch with the search result. Keep both operations on the configured directory and reject referrals and plaintext downgrade. Discard the user’s LDAP password immediately after the attempt, including on errors. [LDAP authentication](https://www.rfc-editor.org/rfc/rfc4513.html) · [LDAP search filters](https://www.rfc-editor.org/rfc/rfc4515.html)

Link the one owner to the immutable entry identifier within the verified directory configuration, such as `entryUUID` or Active Directory `objectGUID`. A login name or DN can locate an entry. Only the verified ID establishes the owner binding. A renamed account can still sign in when it resolves to the linked ID. A deleted and recreated account with the same name or DN must fail until the owner explicitly relinks it. Reject a directory configuration that cannot supply a suitable immutable ID. This setup links only one explicitly verified entry and performs no enrollment or directory sync. Siluet TOTP remains optional for LDAP-only use and applies when enabled. [LDAP entryUUID](https://www.rfc-editor.org/rfc/rfc4530.html) · [Active Directory objectGUID](https://learn.microsoft.com/en-us/windows/win32/adschema/a-objectguid)

## Offline host recovery

Use a separate recovery flow that an operator deliberately starts from the OS host under the installation’s local permissions. The proposed console procedure issues a short-lived, single-use token for a recovery-specific local interaction. A regular server start, an external outage or a failed sign-in never activates recovery. Recovery uses no upstream service or retired password and works when the machine is offline.

Set a new local password for the existing owner, revoke all sessions and pending auth flows and proofs, clear old MFA and recovery material, and disable prior external links until explicitly reverified. Preserve the owner ID, library, provider credentials, jobs and billing records. The owner can enroll TOTP again after recovery. The module spec will define the host invocation and reset transaction.

## Where the trust boundary sits

- **Local access.** Keep the TCP listener on loopback and one explicitly configured canonical origin. Protect HTML, actions, APIs, job streams, previews and direct media/download routes in the server hook or equivalent guarded handlers. Private files stay outside the public static directory. Keep only the minimal health response, public UI assets and the flow-specific claim, sign-in, callback and recovery routes reachable as needed. Validate Host and browser Origin on mutations. Forwarded identity headers alone never authenticate a request. A signed-in browser remains responsible for authorizing billable work. [SvelteKit authentication](https://svelte.dev/docs/kit/auth) · [Bun adapter origin configuration](https://svelte.dev/docs/kit/adapter-bun#Environment-variables-Public-origin-behind-a-proxy)
- **Callbacks.** Register one exact callback such as `/auth/oidc/callback` under the canonical origin. The provider redirects the creator’s browser on the same machine back to Siluet. Use a trusted HTTPS loopback origin for a web client whose provider requires HTTPS. The native-app loopback exception is not a blanket exception for web clients. Verify the supported origin, cookie and callback combination per preset. A LAN listener, remote browser, public ingress or forwarded-header login needs a separate access decision. [OAuth security best practice](https://www.rfc-editor.org/rfc/rfc9700.html)
- **OIDC trust.** Use a maintained OIDC client for authorization code with S256 PKCE. Bind state, nonce, verifier, purpose, expiry and return destination to one browser flow. Validate the exact issuer, signature, audience, expiry, nonce and authorized party when applicable. Match the verified issuer and stable subject within the configured client. Username, email and groups never grant owner access. Request only `openid` and discard provider tokens after validation. Fetch discovery and signing keys only during an explicit test, sign-in or reauthentication, with bounded caching and trusted TLS. Restrict issuer and discovered destinations to the approved provider endpoints, including explicitly approved private-network destinations. Reject unexpected destination changes or redirects before sending credentials. Changes to trusted settings require retesting. [OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html) · [OpenID Connect Discovery](https://openid.net/specs/openid-connect-discovery-1_0.html) · [OAuth security best practice](https://www.rfc-editor.org/rfc/rfc9700.html)
- **Storage.** Keep the optional local password verifier, revocable server-session token digests with their authenticating method and revision, factor state, recovery-code hashes and verified identity bindings in local embedded Turso through focused Drizzle functions. Use an opaque random host-only HttpOnly session cookie, SameSite=Lax for the top-level code redirect and Secure on HTTPS. Apply idle and absolute expiry, session rotation, explicit sign-out and revocation on sign-in method removal, replacement or host recovery. Encrypt TOTP seeds, OIDC client secrets and LDAP service bind credentials with authenticated encryption under an OS-protected key kept separately from the database. Plan backup, restore and key loss together. Rate-limit claim, sign-in, reauthentication and recovery and keep credentials, tokens and raw upstream responses out of client errors, callback diagnostics and logs. [Bun password hashing](https://bun.com/docs/runtime/hashing) · [Turso and Drizzle](https://docs.turso.tech/sdk/ts/orm/drizzle)

## Verification before shipping

The first durable module should pin the Bun, Turso and Drizzle versions it tests. Its acceptance suite should exercise asynchronous Argon2id verification, competing claim transactions over two connections, rollback, and reopening the database to confirm that exactly one owner and session persist.

Use synthetic accounts and pinned, disposable identity services for the following acceptance checks.

1. **Claim and local access.** Confirm exactly one owner after racing claims. Reject expired and repeated claims. Exercise restart and failed migration, plus anonymous access to protected pages, direct files, APIs and streams. Verify offline local sign-in and logout. Onboarding and opening Security issue zero identity-provider calls.
2. **Independent methods and MFA.** Exercise all seven nonempty combinations of local password, OIDC and LDAP. Sign in as the same owner through each enabled method with TOTP off and with TOTP on. Withhold the full session until the enabled factor passes. Reject replayed TOTP steps and recovery codes. Assert the local form never sends credentials to the directory and the LDAP form never verifies a local password. On an upstream error, show failure and make no automatic fallback request.
3. **OIDC trust and identity.** Run each preset’s full browser round trip and an explicit reauthentication against the pinned service. Verify the loopback callback and cookie, exact issuer and client, correct subject and signed `auth_time`. Reject a different subject with the same username or email, invalid TLS, tampered claims, an unapproved discovered endpoint, spent state, and stale or missing `auth_time` for a settings proof. Check Tinyauth’s username and client-ID behavior and the operator’s no-reuse policy. Confirm the authentik subject survives a name change and changes when the account is recreated. A failed candidate leaves the working configuration available.
4. **LDAP trust and identity.** Verify LDAPS and required StartTLS. Reject untrusted TLS, an empty or invalid password, zero or multiple search results, ambiguous or missing entry ID, referral and a replacement entry that reuses the original DN or login. Check that an entry rename preserves the binding when the ID is stable. Search or service bind success alone never yields a session. A failed link leaves the working configuration available and directory passwords stay out of persisted data and logs.
5. **Method changes.** With OIDC alone, LDAP alone and both linked, prove sign-in as the owner before disabling local password. Reject proof from another browser or action, stale candidate or security revisions, expired and replayed proofs, and attempts to remove the last verified method. Race two removals and race a removal against a configuration edit using separate connections. Verify that exactly one valid conflicting mutation can commit and the surviving method remains usable. Inject a transaction failure and verify the prior state, including sessions, is intact. Reject callbacks or bind completions for methods retired while the sign-in was in flight.
6. **External-only and recovery.** Check that the local verifier is gone, direct local login requests fail and all earlier password sessions are revoked. Confirm the new session, if issued, comes from the surviving method. With valid fresh external proof, reenable local sign-in by setting a new password. With every enabled external method unavailable or a factor lost, verify that recovery appears only after deliberate host initiation, works offline, consumes its token once and revokes prior auth material. Verify the same owner ID, gallery files, jobs, provider credentials and billing records after either path.
